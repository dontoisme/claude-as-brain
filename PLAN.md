# Claude-as-Brain — Implementation Plan

A personal knowledge system where **Claude Code is the retrieval layer**, not a note-taking app.

No Obsidian. No plugins. No proprietary format. Just markdown files, a beads database, and a set of commands that make Claude good at operating them.

---

## Why This Is Different

Obsidian-style PKM optimizes for **navigation**: wikilinks, graph view, backlink panes, Dataview queries. You find things by clicking toward them, and the app does literal string matching when clicking isn't enough.

This system optimizes for **retrieval and synthesis**. You find things by asking. The reader is a model that can read fifty notes, rank them, notice that two contradict each other, and tell you so.

That inverts several design rules:

| Obsidian-first | Claude-first |
|---|---|
| Wikilinks are for clicking | Wikilinks are **also** grep anchors for backlink queries |
| Dashboard = live Dataview queries | Dashboard = regenerated by reading the actual files |
| Search = literal match | Retrieval = read, rank, synthesize, cite |
| MOCs hand-maintained | MOCs **Claude-maintained** — same artifact, no staleness tax |
| Structure must be human-navigable | Structure must be human-navigable **and** machine-legible |

The main event becomes the things Obsidian can't do at all: asking a question and getting a synthesized, cited answer; tracing how a belief changed over eight months; walking into a meeting with every prior commitment surfaced.

But note what is **not** in that table: nothing about abandoning the folder structure, and nothing about making files less readable. See the next section — that's a hard constraint, not a nice-to-have.

---

## Hard Constraint: The Markdown Layer Stands Alone

**Markdown is the durable, portable, human-readable source of truth. Beads is an accelerator that could disappear tomorrow without costing you any knowledge.**

Four futures this has to survive, all of them plausible:

1. **Obsidian gets approved.** The vault should light up immediately — graph view, backlinks, Dataview — with zero migration.
2. **You leave the role, or `bd` breaks.** A complete, readable vault remains.
3. **A colleague opens the folder.** They can read it without installing anything or knowing what beads is.
4. **You're on your phone** with any plain markdown app.

Which yields these rules:

- **Full PARA + MOC structure is preserved.** Not flattened, not "optional." `Projects/`, `Areas/`, `Resources/`, `Archive/`, plus `MOCs/`, `Days/`, `Meetings/`, `People/`, `Inbox/`, `Templates/`.
- **Every note is a normal markdown file** with YAML frontmatter and `[[wikilinks]]`. Nothing proprietary, nothing that needs a tool to decode.
- **Anything beads knows has a rendered markdown mirror.** Details below.
- **Templates keep `{{date:YYYY-MM-DD}}` syntax.** See the template note below — this is the forward-compatible choice, not a liability.
- **No file is meaningless without Claude.** If a file only makes sense to a model, it's designed wrong.

## Architecture: Three Memory Layers

The core design idea. Most PKM systems have one layer (notes) and bolt tasks on. This has three, with a clear division of labor.

### Layer 1 — Notes (markdown files)
**What:** prose, context, reasoning, meeting records, research, decisions and their rationale.
**Shape:** long-form. Things you'd want to *read*.
**Retrieval:** Claude greps and reads them on demand.
**Lives in:** `Days/`, `Meetings/`, `Areas/`, `Projects/`, `Resources/`.

### Layer 2 — Beads issues (`bd`)
**What:** commitments. Anything with an owner, a state, or a dependency.
**Shape:** structured records with real status, priority, labels, and a dependency graph.
**Retrieval:** `bd ready`, `bd list`, `bd query`, `bd stale`, `bd graph`.
**Why not just a markdown table:** `Todos.md` cannot answer "what can I actually start right now?" A dependency graph can. `bd ready` excludes blocked, deferred, and in-progress work and returns only genuinely claimable items.

**But it does not replace the markdown.** `Todos.md` survives as a **generated mirror**:

- Beads is canonical for *state* — status, priority, dependencies, who's blocked on what.
- `Todos.md` is a rendered view, regenerated after any write, grouped into the familiar PARA-friendly sections (Due Soon / This Week / Waiting On Others / Ongoing) with `[[wikilinks]]` back to source notes.
- It carries a header: *"Generated from beads — edit via `bd`, not by hand."*

One source of truth, one readable projection. No divergence, because the projection is never hand-edited. If `bd` vanishes you still have the last render, and if Obsidian arrives the file is already a normal linked note.

### Layer 3 — Beads memories (`bd remember`)
**What:** short operational facts you never want to look up twice.
**Shape:** one-liners with a key. *"Fiscal year starts in April." "Dana owns the billing roadmap." "Renewals data lives in the Snowflake `arr_monthly` table."*
**Retrieval:** **automatic.** `bd prime` injects them at session start; `bd hooks install` makes that happen without you asking.

Layer 3 is the non-obvious one and probably the biggest single win. A fact stored with `bd remember "..."` is present in *every future Claude Code session in this folder* — no note to open, no context to load, no `/command` to run. And you add one mid-conversation with a single command, which means the capture cost is near zero, which means you'll actually do it.

**The routing rule, stated once:**
- Will I want to *read* this later? → **note**
- Do I need to *do* this, or is someone owed it? → **bead**
- Should Claude just *know* this, always? → **memory**

## Repo Structure

```
claude-as-brain/
├── README.md               # What this is, how to start
├── CLAUDE.md               # Auto-loaded context (the heart of it)
├── AGENTS.md               # bd onboarding pointer (per `bd onboard`)
├── PLAN.md                 # This file
│
│                           # ---- PARA ----
├── Projects/               # Time-bounded work
├── Areas/                  # Ongoing responsibilities
├── Resources/              # Reference material
├── Archive/                # Inactive
│                           # ---- MOC + support ----
├── MOCs/                   # Maps of Content — Claude-maintained
├── Days/                   # Daily notes, YYYYMMDD.md
├── Meetings/               # YYYYMMDD - Name.md
├── People/                 # Who's who — heavily used when ramping
├── Inbox/                  # Quick captures awaiting routing
├── Templates/              # Note templates (Templater-compatible)
│
├── Dashboard.md            # Generated view (Dataview blocks kept, commented)
├── Todos.md                # Generated mirror of beads
├── INDEX.md                # Navigation for humans
├── Knowledge Changelog.md  # Chronological index of what's been learned
│
├── .obsidian/              # Shipped, minimal — ready if approval lands
├── .beads/issues.jsonl     # Seed issues + memories (plain text, git-tracked)
└── .claude/commands/       # The command set
```

**PARA + MOC is fully intact.** The structure is identical to a conventional Obsidian vault — that's deliberate, so approval day is a no-op rather than a migration.

**What changes is who maintains it, not what it is:**

| Artifact | Obsidian-first | Here |
|---|---|---|
| `MOCs/` | Hand-curated, drifts stale | Claude-maintained during `/weekly-review` — same file, same wikilinks |
| `Dashboard.md` | Live Dataview queries | Regenerated by reading files; Dataview blocks retained but commented out, ready to uncomment |
| `Todos.md` | Hand-edited table | Generated mirror of beads, same table format |
| `Templates/` | Templater fills `{{date}}` | Claude fills `{{date}}` — **identical files** |

### On MOCs specifically

I initially argued Claude synthesizing a topic view on demand beats a hand-maintained hub note. That was wrong, for two reasons:

1. A MOC is the **human** navigation layer. Without Obsidian's graph view, a curated hub note is *more* necessary, not less — it's the only way to browse by topic rather than by folder.
2. A MOC is **curation signal Claude can't fully infer**. "These twelve notes belong together and here's the through-line" is a human judgment; it makes retrieval better, not redundant.

The staleness objection was really an objection to *manual maintenance*, and that's solvable: Claude updates MOCs during weekly review. First-class concept, automated upkeep.

### On templates and `{{date:...}}`

Reversing my earlier call. Keep the Templater syntax and teach Claude to **substitute** it rather than copy it literally.

This is strictly better than stripping it: the templates work identically in both worlds, and if Obsidian + Templater is approved later, they just start working natively with no edits. The only real requirement is that `CLAUDE.md` states the rule explicitly — the actual bug in the original repo was never the syntax, it was that nothing told Claude what to do with it.

## Command Set

Thirteen commands in four groups. The retrieval group is the reason the system works at all.

### Setup

**`/install`** — the unpack step. Turns the cloned distribution into your brain. See the Install model below.

### Retrieval — replaces what the app used to do

**`/ask <question>`**
The flagship. Greps and reads across the vault, answers in prose, **cites the source notes**. Says "I found nothing on that" rather than inventing an answer. Distinguishes what you wrote from what it inferred.
*Named `/ask`, not `/recall`, to avoid colliding with `bd recall`.*

**`/thread <topic>`**
Traces how thinking on a topic evolved chronologically. Reads every note mentioning it in date order and reports the arc — what you believed in March, what changed in May, what's currently unresolved. Flags contradictions explicitly. Obsidian cannot do this at any price.

**`/prep <meeting|person|topic>`**
Inverse of `/process-meeting`. Before a call: prior notes, open beads involving those people, unresolved questions, commitments you made and haven't closed. Ends with "here's what you owe them, and what they owe you."

**`/brief`**
Morning state-of-the-world: yesterday's note, `bd ready`, anything due, anything `bd stale` flagged, Inbox depth. Short by design — a page, not a report.

### Capture — getting things in cheaply

**`/capture`** — thought → Inbox, or straight to `bd q` if it's clearly a task. Zero friction, no routing questions.
**`/save-to-brain`** — session insight → routed note + Knowledge Changelog + daily note link. Prompts to `bd remember` if the insight is a durable operational fact rather than prose.
**`/process-meeting`** — raw notes → structured meeting note + beads issues for every commitment, with `--deps` where one blocks another.
**`/daily-note`** — today's note, seeded with `bd ready` and yesterday's carryover.

### Maintenance — the stuff Obsidian did silently

**`/rebuild-dashboard`** — regenerates `Dashboard.md` by reading real files. Replaces Dataview, but can also editorialize: "3 of these projects haven't moved in a month."
**`/sync-todos`** — renders beads state into `Todos.md` as a readable, wikilinked table. Called automatically by any command that writes beads.
**`/update-mocs`** — refreshes `MOCs/` from what's actually in the vault: adds new notes to the right maps, flags clusters that deserve a new MOC, removes links to deleted notes. This is what keeps MOCs first-class without a maintenance tax.
**`/link-check`** — broken wikilinks, orphaned notes, notes referenced but never created. Obsidian showed you these for free; nothing does now, and link rot is silent.
**`/weekly-review`** — the Friday synthesis, now with `bd stale` and the beads graph as inputs, and calling `/update-mocs` and `/sync-todos` at the end.
**`/ramp`** — new-role capture: org map, who owns what, acronyms, systems, unwritten norms. Aggressively suggests `bd remember` for anything you'll need repeatedly. Expected to fall out of use after ~90 days; that's what ramping means.

## The Beads Superpower

Verified against `bd` 1.0.2.

### Why it beats a markdown checklist

A `Todos.md` table is a list of strings. Beads is a queryable graph with state. Concretely, it can answer questions markdown can't:

```bash
bd ready                  # what can I actually start? (blocker-aware)
bd stale                  # what have I quietly abandoned?
bd graph                  # what's blocking the thing I care about?
bd query <expr>           # structured filtering
bd search "renewals"      # text search across all issues
```

`bd ready` is the one that earns its keep. It excludes in-progress, blocked, deferred, and hooked issues — so it returns *genuinely claimable work*, not "everything that isn't done." (Note: `bd list --ready` is **not** equivalent; it only filters by status.)

### The three integration points

**1. Auto-injected context.** `bd hooks install` injects `bd prime` at session start, so every Claude instance in this folder opens already knowing your workflow state and stored memories. `AGENTS.md` only needs the minimal pointer that `bd onboard` prints — not a full copy of the instructions. Keeps context lean and always current.

**2. Commitments become first-class.** `/process-meeting` stops writing action items into a table and starts creating real issues with owners, priorities, and dependencies. "I can't start the pricing doc until Legal answers" becomes a modeled edge, so `bd ready` correctly hides it until it's actionable.

**3. Frictionless durable facts.** `bd remember "Dana owns billing"` mid-conversation, and it's in every session forever. This is the layer that makes the system feel like it knows you.

### Gotchas to bake into the docs

So a fresh Claude instance doesn't fumble:

- `bd create`, not `bd add`
- Dependencies: `--deps` at create time, or `bd dep add <blocked> <blocker>` afterward. **`bd update` does not accept `--deps`** — use `bd dep add`, don't recreate the issue.
- Tasks can depend on tasks, not on epics. `--deps <epic-id>` warns and silently skips. Depend on the epic's relevant child.
- `--notes` on create (not `--comment`); `--append-notes` on update (plain `--notes` overwrites)
- `-l` / `--labels` for categorization; there is no `--tag` flag on create
- `bd q` for quick capture — returns only the ID, ideal for scripted capture
- `--parent <id>` at create time for hierarchy; children inherit parent labels

### Resolved: `Todos.md` stays

Earlier draft recommended dropping it, reasoning that two task systems means neither gets trusted. The concern is real but the conclusion was wrong — it would have left the vault with **no human-readable task layer at all**, breaking every one of the four durability futures above.

The fix is the generated-mirror pattern: beads is canonical for state, `Todos.md` is a rendered projection regenerated on write and never hand-edited. That's one source of truth with a readable view, not two competing systems.

`/sync-todos` handles the render, and `/process-meeting`, `/brief`, and `/weekly-review` call it after any write.

## CLAUDE.md Design

The most important file. It must establish four things:

1. **This is a thinking instance, not a coding instance.** No builds, no tests, no refactoring offers. Default behaviors: ask clarifying questions, challenge vague thinking, summarize before filing. A Claude that acts like it's in a code repo is subtly wrong here.
2. **Obsidian is not currently installed, but the vault must stay compatible with it.** Wikilinks still get maintained — they're grep anchors now and clickable links later. `{{date:YYYY-MM-DD}}` in a template is a **substitution directive**: compute the value and write the result, never copy the literal string into a note. Don't "simplify" the vault by removing structure that only pays off under Obsidian.
3. **The three-layer routing rule** — note vs. bead vs. memory, with examples.
4. **Proactive capture.** Offer to save after real learning moments; specifically offer `bd remember` when something is a durable operational fact. Don't offer on routine file navigation.

Plus the customizable blocks: what the vault is for, the Areas list, tag vocabulary, current context.

## Implementation Phases

**Phase 1 — Foundation**
`README.md`, `CLAUDE.md`, `AGENTS.md`, full PARA + MOC folder skeleton with `README` stubs, Templater-compatible templates, minimal `.obsidian/` config, `.gitignore`.

**Phase 2 — Retrieval commands**
`/ask`, `/thread`, `/prep`, `/brief`. The differentiators — build and test these before anything else, since they're what justifies the system.

**Phase 3 — Capture commands**
`/capture`, `/save-to-brain`, `/process-meeting`, `/daily-note` — ported from the Obsidian repo, rewritten for beads-backed commitments.

**Phase 4 — Maintenance commands**
`/rebuild-dashboard`, `/sync-todos`, `/update-mocs`, `/link-check`, `/weekly-review`, `/ramp`.

**Phase 5 — Beads wiring and `/install`**
The `/install` command, the seed `.beads/issues.jsonl` (issues + example memories), `AGENTS.md` from `bd onboard`, plus a `Beads Guide.md` documenting the workflow and gotchas above. Also the graceful-degradation path for when `bd` isn't installed.

**Phase 6 — Seed content and docs**
A few example notes so `/ask` and `/thread` have something to chew on, a `START HERE.md`, and a README that leads with the retrieval demo rather than the folder diagram.

**Phase 7 — Validation**
Actually use it for a week. Every command run against real content. Fix what's annoying before publishing.

Plus an explicit **Obsidian compatibility pass**: open the vault in Obsidian once, on a personal machine, and confirm the four durability futures hold — links resolve, MOCs and Dashboard render as sensible notes, `Todos.md` reads correctly, templates behave. Anything that only works via Claude is a design bug, and this is how it gets caught before publishing rather than on approval day.

## The Install / Unpack Model

The repo ships as a **distribution**, not a working vault. Cloning gets you a complete example; `/install` turns it into yours.

This turns out to align exactly with how beads already wants to work. `.beads/issues.jsonl` is beads' **git-tracked export format** — `bd import` with no arguments reads precisely that path. So the seed isn't a binary database checked into git; it's plain-text JSONL that's readable, diffable, and reviewable in the repo, and unpacks into a local Dolt DB on install.

Better still, **memory records round-trip in the same file.** Lines tagged `"_type":"memory"` import as persistent memories, equivalent to `bd remember`. So the repo can ship example Layer-3 memories that unpack alongside the issues — which is the only way to *demonstrate* the auto-injected memory layer rather than just describe it.

### What ships

```
.beads/issues.jsonl     # Seed issues + memories, plain text, git-tracked
                        # No .db — that's generated locally, gitignored
```

### `/install` — the unpack command

Interactive, and the first thing a new user runs:

1. **Ask about their work** — role, domain, what the vault is for
2. **Fill the 👉 blocks in `CLAUDE.md`** — purpose, Areas, tag vocabulary
3. **Create their real Areas** in `Areas/`, from their answers
4. **Set up beads** (if `bd` is present):
   - `bd init --prefix <their choice>`
   - `bd import` — unpacks the seed issues and memories
   - `bd setup claude` — wires up Claude integration
   - `bd hooks install` — auto-injects `bd prime` at session start
5. **Offer to clear the examples** — remove seed notes and demo beads, or keep them for a first `/ask` run
6. **Confirm the four durability futures** hold — structure intact, links resolve

Seed content is therefore explicitly *scaffolding*: enough for `/ask` and `/thread` to demo convincingly on first run, and designed to be deleted in one step.

### Note for the work clone

`bd init --stealth` configures `.git/info/exclude` so beads artifacts are never committed. Worth knowing for a private work clone where you'd rather the tracked repo stay pure markdown.

## Decisions

**Resolved:**

1. **Repo name** — `claude-as-brain`
2. **Seeded beads** — yes, as `.beads/issues.jsonl`, unpacked by `/install`
3. **Beads is optional but strongly recommended** — commands degrade to markdown-only behavior when `bd` isn't on PATH, and say so rather than failing
4. **`Todos.md`** — stays, as a generated mirror of beads
5. **MOCs** — first-class, Claude-maintained
6. **Templates** — keep Templater `{{date:...}}` syntax

**Still open:**

7. **Exact seed content** — how many example notes, and in what domain. Needs to be generic enough not to read as someone else's job, specific enough that `/thread` has a real arc to trace.

## Public Template vs. Private Vault

This repo is the **public template**. Your actual brain is a separate clone with a private remote, or no remote at all.

Nothing specific to your employer — customer names, roadmap detail, org structure, internal metrics — belongs here. Keeping the two physically separate is the safeguard, because one is meant to be pushed publicly and the other emphatically is not.

If you work somewhere with a data-handling policy, note that it applies to a folder of markdown exactly as it would to any other tool holding the same content.
